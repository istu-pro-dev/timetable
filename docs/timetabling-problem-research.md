# Исследование: ключевые проблемы составления расписания
### Основа для функциональных/нефункциональных требований

---

## 1. Постановка задачи

Составление расписания (в англоязычной литературе — *Timetabling*, конкретно для вузов — *University/Course Timetabling Problem, UCTTP*) относится к классу NP-трудных задач комбинаторной оптимизации. Формально: есть множества ресурсов (группы, преподаватели, аудитории) и множество занятий, которые нужно расставить по временным слотам так, чтобы:

- не нарушались **обязательные** ограничения (hard constraints) — иначе расписание физически невыполнимо;
- по возможности соблюдались **желательные** ограничения (soft constraints) — они определяют не факт существования расписания, а его *качество*.

Это разделение — hard/soft — является общепринятым в научной литературе и должно лечь в основу архитектуры бизнес-логики: сначала генерация допустимого решения, затем его оптимизация по критериям качества.

В России задача имеет специфику: ограничения по студентам обычно рассматриваются на уровне **групп**, а не отдельных студентов (в отличие от западных вузов с индивидуальным выбором курсов), а расписания часто до сих пор составляются вручную отделами до 20 человек, что и порождает основные проблемы.

## 2. Жёсткие ограничения (Hard Constraints)

Нарушение любого из них делает расписание некорректным «по определению» — такие случаи нужно физически блокировать в UI/логике, а не просто подсвечивать.

| № | Ограничение | Суть |
|---|---|---|
| H1 | **Занятость преподавателя** | Один преподаватель не может вести два занятия одновременно |
| H2 | **Занятость группы/потока** | Группа (или объединённый поток) не может быть на двух занятиях одновременно |
| H3 | **Занятость аудитории** | В одной аудитории в один слот — не более одного занятия |
| H4 | **Доступность ресурса по времени** | Если преподаватель/аудитория недоступны в конкретный слот (внешний совместитель работает только по вторникам и четвергам, аудитория закрыта на ремонт) — занятие туда не ставится |
| H5 | **Совместимость по типу аудитории** | Лекция/лабораторная/семинар должны проводиться в подходящем по типу помещении (лаборатория, спортзал, компьютерный класс и т.д.) |
| H6 | **Вместимость аудитории** | Число студентов группы не должно превышать вместимость аудитории (в строгой версии — hard, в мягкой — штрафуется как soft) |
| H7 | **Полнота расстановки** | Все занятия учебного плана за период должны быть расставлены в полном объёме (число часов/занятий по плану = число занятий в расписании) |
| H8 | **Отсутствие дублей** | Занятие по одной дисциплине для одной группы в рамках недели не может повториться в тот же день дважды сверх учебного плана |

## 3. Мягкие ограничения / критерии качества (Soft Constraints)

Это как раз то, что определяет **бизнес-ценность** продукта — само по себе допустимое расписание собрать не так сложно, ценность в том, чтобы оно было *удобным*. Ниже — ключевые критерии, которые в профильной литературе и у существующих российских систем автоматизации (например, «1С:Автоматизированное составление расписания. Университет») закладываются как целевые функции оптимизации.

### 3.1 Минимизация «окон»
Пустые промежуты между занятиями в один день у группы или у преподавателя — главная жалоба пользователей вручную составленных расписаний. Это один из основных критериев оптимизации в промышленных системах.

### 3.2 Минимизация переходов между корпусами
Географическое расположение корпусов должно учитываться так, чтобы в течение дня у группы/преподавателя было минимум перемещений между зданиями; в идеале — занятия одного дня должны группироваться в одном корпусе.

### 3.3 Компактность нагрузки преподавателя
Оценивается через количество дней, в которые преподаватель полностью свободен (для подготовки, методической и научной работы), — чем больше цельных свободных дней, тем выше качество расписания для преподавателя.

### 3.4 Равномерное распределение по дням недели (Minimum Working Days)
Занятия по одной дисциплине не должны «слипаться» в один-два дня — должны быть распределены на заданное минимальное число дней в неделе, чтобы избежать перегрузки в один день и провала в другой.

### 3.5 Компактность/смежность занятий по учебному плану (Curriculum Compactness)
Занятия, относящиеся к одному учебному потоку/curriculum, желательно ставить подряд, без «разрывов» между ними в течение дня.

### 3.6 Стабильность аудитории (Room Stability)
Все занятия по одной дисциплине у одной группы желательно проводить в одной и той же аудитории — снижает переходы и путаницу, упрощает логистику (доска, оборудование).

### 3.7 Избыточность вместимости
Минимизация разницы между вместимостью аудитории и фактическим числом студентов — не выделять поточную аудиторию на 200 мест под группу в 15 человек, если есть меньшая свободная.

### 3.8 Учёт «крайних» слотов
Желательно не ставить занятия первой парой (особенно для младших курсов) или последней парой в день, если этого можно избежать — считается отдельным штрафуемым критерием в ряде моделей (ITC-2007: Late Events).

### 3.9 Минимизация количества используемых помещений
Альтернативный критерий оптимизации — не количество окон, а компактность использования фонда аудиторий (актуально при дефиците помещений).

### 3.10 Учёт пожеланий и предпочтений
Пожелания преподавателей (конкретные дни, только первая/вторая половина дня — особенно критично для совместителей) и пожелания по «предпочтительному» времени для групп/кафедр — не жёсткое ограничение, но должно штрафоваться при нарушении.

### 3.11 Двусменность и параллельные потоки
При обучении в 2+ смены — соблюдение баланса нагрузки между сменами; при потоковых лекциях — корректное объединение нескольких групп в одно занятие без конфликтов внутри объединённых групп.

### 3.12 Разбиение на подгруппы
Занятия, где группа делится на подгруппы (например, иностранный язык, физкультура) — подгруппы должны идти параллельно и без взаимных конфликтов по ресурсам.

## 4. Ключевые проблемы ручного составления расписания (как есть сейчас)

1. **Долгий цикл составления** — процесс вручную занимает от нескольких дней до нескольких недель; при этом задействуется целый отдел (по опыту крупных вузов — до 20 человек).
2. **Ошибки и коллизии** — пересечения по преподавателю/аудитории/группе, которые человек физически не может отследить при большом числе занятий (масштаб задачи — комбинаторный, поиск вручную неэффективен).
3. **Долгая и болезненная реакция на изменения** — при любом изменении (заболел преподаватель, аудитория стала недоступна, изменился учебный план) пересчёт вручную требует повторного прохода по всей цепочке связанных занятий.
4. **Нет прозрачной оценки качества** — «хорошее» и «плохое» допустимое расписание визуально неотличимы без специальных метрик (число окон, переходов, компактность), поэтому качество сильно зависит от квалификации конкретного диспетчера.
5. **Консолидация расписаний разных уровней** — расписания кафедр нужно свести в расписание факультета/института/вуза в целом, устранив коллизии по общим ресурсам (аудитории общего фонда, совместители, потоковые занятия для смешанных групп) — вручную это отдельный трудоёмкий этап.
6. **Дефицит и неоптимальное использование аудиторного фонда** — при ручном подходе сложно одновременно учитывать тип, вместимость и загруженность каждой аудитории по всем слотам недели.
7. **Слабая поддержка сценариев "что если"** — нет возможности быстро сравнить несколько вариантов расписания (оптимистичный/пессимистичный сценарий, разные приоритеты критериев) и выбрать лучший.
8. **Оповещение об изменениях** — при ручном процессе информирование студентов и преподавателей об изменениях в расписании происходит с задержкой и через разрозненные каналы.

## 5. Как это ложится в требования к продукту (черновой каркас)

### Функциональные требования (укрупнённо)
- Ведение справочников: группы/подгруппы, преподаватели, дисциплины, аудитории (с типом и вместимостью), корпуса, учебные планы.
- Загрузка учебного плана и ограничений/пожеланий ресурсов (преподаватели, группы, аудитории).
- Автоматическая генерация допустимого расписания с проверкой всех hard-ограничений (раздел 2).
- Оптимизация по одному или нескольким soft-критериям (раздел 3) с возможностью задавать их приоритет/веса.
- Ручной и смешанный режим редактирования (drag&drop) с мгновенной проверкой на коллизии при перемещении занятия.
- Сравнение нескольких вариантов расписания и выбор лучшего по агрегированной метрике качества.
- Консолидация расписаний разных подразделений в общее расписание вуза с устранением коллизий по общим ресурсам.
- Учёт потоковых занятий и разбиения на подгруппы.
- Учёт максимально допустимого числа занятий в день для группы/преподавателя.
- Быстрая замена/перестановка занятий (в т.ч. при болезни преподавателя, отмене) с автоматическим пересчётом связанных занятий.
- Уведомления об изменениях в расписании (email/push) для затронутых студентов и преподавателей.
- Просмотр расписания и ввод пожеланий преподавателями/студентами через веб-интерфейс.
- Отчётность: использование аудиторного фонда, нагрузка преподавателей, проведённые занятия.

### Нефункциональные требования (укрупнённо)
- Производительность генерации расписания на масштабе реального вуза (сотни групп/преподавателей/аудиторий) — приемлемое время пересчёта.
- Возможность инкрементального пересчёта (не всего расписания целиком) при точечных изменениях.
- Разграничение доступа по подразделениям/документам.
- Импорт/экспорт справочников и учебных планов (Excel/XML) для интеграции с существующими вузовскими системами.
- Аудит изменений (кто и когда менял расписание).
